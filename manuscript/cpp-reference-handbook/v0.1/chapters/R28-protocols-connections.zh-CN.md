# 第28章 协议与连接

网络请求经过多个独立边界：名字解析、路由与传输、身份验证、报文解析、业务处理。某一层成功只能排除该层的一部分问题，不能直接证明请求已经由业务执行。

**版本与范围**：TCP 依据 RFC 9293，TLS 1.3 依据 RFC 8446，HTTP 语义／1.1／2／3 依据 RFC 9110–9114；不是 C++ 标准网络库。**先修**：字节与端序、OS I/O、错误与截止时间。首次读第1至4节，线上定位查第5节。

## 1 DNS、IP、端口与路由

DNS 查询把名称和记录类型映射到记录集合，A／AAAA 分别给出 IPv4／IPv6 地址；同一名字可返回多个地址，缓存受 TTL 等规则影响。解析器还可能经系统配置、hosts 或本地缓存得到结果，不能把每次 getaddrinfo 都视为一次外部 DNS 请求。DNS 成功不证明地址当前可达或对应服务正常。[DNS 基础 RFC 1034](https://www.rfc-editor.org/rfc/rfc1034)。

IP 负责数据报寻址与转发，路由决定下一跳，不保证交付、顺序或业务身份。IPv6 地址为128位，不能装入 IPv4 的32位槽位；地址解析应处理地址族和候选集合。接口 MTU 限制一跳可承载的包大小，路径上的限制影响传输，不能根据以太网常见数值硬编码任意公网报文。[IPv6 RFC 8200](https://www.rfc-editor.org/rfc/rfc8200)。

端口属于传输层，用于区分端点；TCP 与 UDP 有各自命名空间。一个连接通常由源／目的地址与端口以及传输协议识别，NAT 和代理可改变可见端点。服务通过 HTTP Host 或 TLS 名字等另辨身份，因此“直接改成 IP 地址”可能改变认证或虚拟主机路由。

故障定位要固定观察位置。客户端、负载均衡器与源站看到的连接可能不同；代理可先与客户端完成握手，再建到上游的连接。因此客户端 connect 成功只说明到当前对端这一段建立，不保证整个后端链路成功。日志记录逻辑目标、实际端点和代理，避免把两个连接合并为一次握手。

地址缓存与连接池属于不同寿命：DNS更新后，已有连接仍可能通向旧端点。迁移服务时结合缓存、连接空闲寿命与服务端退出协议评估切换窗口，不能只改 DNS 就假定所有客户端立即切换。

## 2 TCP 与 UDP：传输给应用什么

TCP 给应用提供有序可靠字节流，重传与排序不保留 send 调用边界；一条消息可被多个 recv 取到，多条消息可一次读到。连接建立通常经 SYN、SYN-ACK、ACK，但成功 connect 不证明服务器已经开始处理业务请求。连接关闭的发送方向与接收方向分别管理，FIN 表示有序结束一个发送方向，RST 是异常终止信号；已经收到的数据仍需按应用协议处理。[TCP RFC 9293 §3.1、§3.5、§3.6](https://www.rfc-editor.org/rfc/rfc9293)。

流量控制限制发送方不超过接收方可承受的窗口；拥塞控制关注网络负载，目标不同。网络重传只处理传输丢失，不能替代业务重试；TCP ACK 确认的是接收端传输进展，不能证明数据已持久化或交易已提交。TIME_WAIT 是协议正常状态之一，数量上升需结合连接创建与关闭速率分析，不能一见就判资源泄漏。

| 能力 | TCP | UDP |
| --- | --- | --- |
| 应用读取单位 | 字节流，自行分帧 | 数据报，保留报文边界 |
| 可靠与顺序 | 传输层处理，但连接可失败 | 不保证交付、顺序或去重 |
| 建连 | TCP 建立连接状态 | 基础 UDP 无握手；socket connect 可仅设置对端 |
| 大报文 | 分段后仍呈现字节流 | 避免依赖 IP 分片，需尺寸／路径策略 |
| 工作选择 | 请求响应、文件、可靠流 | 可容忍丢失、或上层自行提供完整协议 |

UDP 不保证“必然更快”。使用它需处理丢失、重排、重复、拥塞与报文截断；QUIC 等协议可在 UDP 上实现可靠传输，不能把 UDP 的基础性质套给整个 QUIC。[UDP RFC 768](https://www.rfc-editor.org/rfc/rfc768)、[QUIC RFC 9000](https://www.rfc-editor.org/rfc/rfc9000.html)。

## 3 TLS：机密性、完整性与身份边界

TLS 1.3 协商密钥与参数，保护记录内容，并支持基于证书等方式的对端认证。客户端需要验证证书链、有效期和目标名字，不能因“流量已经加密”跳过身份检查。TLS 不处理业务权限，不保护端点解密后的内存，也不使应用消息自动完整。

ALPN 等协商决定上层协议；客户端与服务端支持版本不一致可在应用请求前失败。恢复会话可减少握手成本，TLS 1.3 的0-RTT early data存在重放风险，不能把可重放业务当一次执行。TLS 记录边界不是业务分帧边界；关闭与截断要交给 TLS 库按协议解释。[TLS 1.3 RFC 8446 §2、§4、§8](https://www.rfc-editor.org/rfc/rfc8446)。

## 4 HTTP 版本、报文完整性与连接复用

HTTP 的方法、状态码、字段与语义跨版本相关；传输编码与多路复用却不同。响应状态2xx也只能按具体接口说明解释业务成功；代理和缓存可能参与，不一定是源站直接回答。[HTTP 语义 RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html)。

| 版本 | 常见承载与组织 | 检查边界 |
| --- | --- | --- |
| HTTP/1.1 | TCP 上消息；HTTPS 加 TLS | Content-Length／chunked 等定界；复用前读完本消息 |
| HTTP/2 | 一条 TCP 连接上二进制帧与多个流 | 有流量控制；TCP 丢失可影响多个流的交付 |
| HTTP/3 | QUIC 上多个流，QUIC 使用 UDP | 独立流减少跨流传输阻塞，但资源／拥塞仍可共享 |

HTTP/1.1 不能把 recv 返回0普遍当正常完整响应：是否完整要看消息定界；不正确处理长度或 Transfer-Encoding 会导致解析分歧和安全问题。HTTP/2 与3 的帧并不等于每次网络读取结果，宜使用经过验证的协议库。[HTTP/1.1 RFC 9112 §6](https://www.rfc-editor.org/rfc/rfc9112.html)、[HTTP/2 RFC 9113](https://www.rfc-editor.org/rfc/rfc9113.html)、[HTTP/3 RFC 9114](https://www.rfc-editor.org/rfc/rfc9114)。

连接池减少握手，但要限定每目标连接／流数量、空闲寿命与获取等待，并淘汰失效连接。复用不是无限并发；一条慢连接、服务端流限制或前一消息未读完，都可能增加队列等待。将“取池连接的耗时”单独记录，才不会把本地排队误判成网络延迟。

消息完整与业务成功用两份证据确认。完整响应说明协议解析得到可消费消息；业务可能仍报告拒绝、部分成功或稍后执行。HTTP 202等状态需按接口文档继续查询，不应让传输层收到响应直接完成业务状态机。反过来，结果未知不代表未执行，重试条件需接到 R29 的幂等与查询方案。

自定义协议需记录版本、消息类型、长度、字节序与错误响应，规定未知字段如何处理。两端都运行 C++ 也不意味着可直接发送 sizeof(struct) 个字节；填充、大小和平台差异仍在，见 R24。

## 5 故障应分层取证

| 现象 | 检查依据 | 不充分的结论 |
| --- | --- | --- |
| 域名解析失败 | 记录类型、解析器、缓存、错误码 | 不等于远端服务崩溃 |
| DNS 成功但连接超时 | 候选地址、路由、防火墙、监听、期限 | 名字正确不保证可达 |
| TCP 成功而 TLS 失败 | 协议版本、证书、名字、时间、ALPN | 不能通过关闭验证“修复”身份问题 |
| TLS 成功而 HTTP 异常 | 报文定界、状态、代理、目标路由 | 加密不证明业务结果 |
| 间歇性慢请求 | DNS／建连／握手／排队／首字节分段耗时 | 总耗时不能定位单层 |
| 连接很多但吞吐低 | 流限制、池等待、背压、重试放大 | 增加连接数不保证容量增加 |

本章经 RFC 来源核验，未进行外网请求或协议栈实测。socket 接口与业务重试见 R29；端序编码见 R24；超时计算见 R19。
