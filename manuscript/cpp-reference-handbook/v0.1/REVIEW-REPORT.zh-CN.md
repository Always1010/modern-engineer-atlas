## 1 结论：需要调整全书的编写方式

当前首稿的主要偏差，是把“规则、边界、工程建议和综合验证程序”组织成了正文主体，却没有稳定建立“介绍对象是什么、如何分类、基本写法是什么、常用操作在哪里查”的骨架。已有知识并非全部无效，但读者经常在学会基本操作之前，先遇到一组限制、复杂条件或工程责任。

用户举出的容器、线程同步和前几章批注，揭示的是全书的编辑问题。解决范围应覆盖语言规则、对象与资源、全部标准库、并发、系统、网络以及构建调试。仅补 vector 的成员表、换几处标题，或把两份旧笔记搬进正文，不能完成这次修整。

建议以**内容结构重构为主，文字压缩、代码整理、图表重做和统一排版同步进行**。保留已核对的有效知识、图源和程序；按新的知识分类重新安排入口；把常用对象和操作补成可查条目；将机制、例外和工程专题移到合适层级。32 个旧章号用于追踪迁移，不把“必须仍有 32 章、183 个二级标题、134 页”作为新稿约束。

本报告的主体是全书解决方案。第 4 节给出系统性诊断，第 5—9 节确定新结构、32 章的调整方向和编辑规则，第 10—11 节确定实施与验收；附录保留用户具体批注及旧笔记需要校正的技术点。

## 3 从局部意见提炼出的全书原则

### 3.1 用户真正需要的手册

读者应能沿两条路径使用同一份正文：第一次接触时，按基础概念和常用写法逐步学习；工作中已知名称时，通过对象、符号、头文件和任务索引直接查到对应条目。两条路径共享知识，不分别维护一份教程和一份参考资料。

“专业、简洁、详细”应同时成立：专业靠准确名称、明确分类和一致维度；简洁靠一个单元解释一个主要问题；详细靠常用对象与操作有完整的查阅位置。删掉必要条件不叫简洁，把多个主题压进表格不叫专业，把测试程序拉长不叫覆盖完整。

### 3.2 局部问题怎样推广

| 用户观察 | 提炼出的全书规则 | 应用范围 |
| --- | --- | --- |
| 容器缺类别、具体类型和成员层次 | 先形成对象分类，再按对象展开，不用一张选型表替代介绍 | 所有库类型、同步设施、系统概念、协议与工具 |
| 初始化、参数、函数没有讲清 | 语法或接口必须就地可查，明确输入、结果和关键条件 | 语言写法、成员函数、自由函数、OS API、工具命令 |
| 表格先写做法、对象不清 | 同表的行属于同一类实体，列使用一致比较维度 | 全部 87 张表格逐张处理 |
| 代码看不出用途，综合内容太多 | 示例先交代任务，每个基础示例只突出一个操作 | 语言、库、并发；系统和工具采用合适的演示形式 |
| 基础术语、类型数据、堆栈等解释不足 | 首次出现先定义，不能用专业名词替代解释 | 全书首次术语与先修知识 |
| 正文“废话多”、顺序不清 | 基础用途先于复杂限制；一项知识有一个主要维护位置 | 全书段落、图注、例子、排障及附录 |
| 标题不像手册 | 标题写专业对象或机制名称，阅读建议进入正文 | 篇、章、二级条目、图表标题和索引 |
| 后面也大多有类似问题 | 修订单位是全书知识结构，局部批注是验证样本 | 所有 32 章及目录、索引、版式生成器 |

### 3.3 不机械套用容器模板

不同内容采用不同条目模板：语言规则需要语法与语义；库类型需要声明、构造及成员分组；系统机制需要实体与工作过程；工具需要命令、操作和结果。TCP 没有构造函数，GDB 没有容器失效规则，不能为了全书整齐强行填同样的字段。

“对象先行”的对象可以是 `std::optional`，也可以是初始化类别、进程、文件描述符、TCP 连接或调试命令。共同要求是读者能明确知道当前条目在解释什么。

## 4 全书诊断：表现、原因与修订责任

以下是扩大阅读后确认的共同模式，不表示每章的每个条目都同样差。已有清楚的对比表、机制图和可验证程序应按实际价值保留。

### P0-01 知识覆盖以宽泛主题为单位，具体对象没有稳定入口

**证据**：R06 的控制语句主要集中在速查表；R09 将三种智能指针主要按职责合并介绍；R16 一个大节覆盖排序、选择、分区、二分、集合及堆；R19 在一章内密集安排 chrono、流和 filesystem。容器与同步设施只是这一模式的两处实例。

**影响**：“提过某个名称”容易被误计为“已介绍这个对象”。读者无法稳定定位声明、初始化和常用操作，也难以判断某项功能是否被遗漏。

**原因**：目录主要登记宽主题；缺少按具体对象和操作审核的内容清单。

**修订**：先建立分类与具体条目清单，再拆分节或章。每个列入展开范围的对象必须有独立入口；只索引的低频对象明确标记，不能用集合段落冒充已展开内容。

### P0-02 工程约束前置，基础使用路径不足

**证据**：R10 在基础函数/类模板写法充分展开前进入推导与实例化；R24 从执行成本与优化约束进入，CPU 基础模型偏薄；R29 的主要完整程序是分帧解析器，socket 创建、连接、接收的基本接口路径不够完整；R31 命令映射多，最小调试过程不足。

**影响**：初学者先知道不能做什么，仍不知道应该怎样开始。工作读者也难以查到正常操作的最短路径。

**修订**：入口统一为“对象定义 → 基础操作 → 结果 → 必要条件”，再进入机制、典型错误与工程专题。涉及有效性的条件仍贴近操作，不能一律挪到末尾。

### P1-01 表格承担了不适合它的叙述任务

**证据**：R01 将声明、定义与位置/链接策略混列；R02 合并多种基础类型；R17 将类型与函数混在同一入口表；R18 将多种接口信息压在同一单元格；R23 的关闭阶段与状态表需要结合明确流程才能读懂。

**影响**：同列并非回答同一个问题，单元格成为短段落，读者需要逐字阅读却得不到横向比较收益。

**修订**：逐表判定保留、拆分、转条目、转流程图或删除。保留 R08 操作对比、R11 异常保证、R17 optional 常用操作、R28 HTTP 版本等有明确比较任务的表，按实际条目补充必要信息。

### P1-02 例子偏向综合核验，基础代码单元不足

**证据**：R07 的对象模型程序、R11 的事务与异常注入、R23 的执行器、R29 的分帧解析器同时承担多种任务；R18 的完整程序组合解析、随机数及字节编码；R31 的算术检查程序不能直接示范一次调试会话。R15 的 ranges 用法有较长行内代码，查阅与阅读都不便。

**影响**：完整程序验证了行为，却没有替代“我查这个接口应该怎么写”的短例子。测试包装和控制流程分散了注意力。

**修订**：基础操作用短例；机制用局部例；综合程序移到章末“组合应用”或配套源码并保留链接。正文解释用途、关键步骤和结果，验证脚本留在 QA/构建说明。

### P1-03 重复提醒与跨章重复占用基础解释空间

**证据**：对齐/对象表示在 R02 与 R24 重叠；字节序与编码在 R18、R24 交叉；期限与取消在 R19、R20、R23、R29 重复；事件循环平台机制在 R23 与 R26 交叉；基础算术检查在 R04、R31 的例子中重现。

**影响**：同一规则有多个版本，读者反复读警示，却未得到相应对象的完整基础资料。增加后续维护时的矛盾风险。

**修订**：确定主要维护章节；其他章节只保留当前操作所需条件、局部应用和精确链接。判断一段是否保留，要看它是否新增定义、操作、结果、成立条件或必要解释。

### P1-04 分层与术语策略没有在条目中持续执行

**证据**：现有阅读指南已有首次/后查路径，但 R07 的基础类写法与对象模型、R10 的基础模板与复杂查找规则、R19 的基础时间接口与持久化/时区、R23 的基本异步模型与框架责任仍交织。用户批注中的 ODR、字节等问题也属于首次解释不足。

**修订**：每个条目标注阅读层级与版本；首次术语定义由主题归属决定；后文给简短提示和链接。不能仅给整章标 FIRST 就认为层级完成。

### P1-05 原有规范正确，但缺少执行约束

**证据**：[EDITORIAL-SPEC.md](EDITORIAL-SPEC.md) 已要求最小例子、签名、参数返回值、相关条件，并明确不能压缩宽泛主题。然而成稿仍出现上述结构。规范还要求保留 R13 样章质量，样章本身也需要按此次标准复审。

**原因**：章完成、编译通过、图存在、目录数量对齐，不能证明每个对象已经可查；缺少条目级编辑验收。

**修订**：把规范落实为条目清单、表格处理记录、主题归属、抽查任务和统一编辑审阅。已有样章是可复用材料，不作为免审的标准答案。

### P2-01 排版以当前篇幅补丁为主，需要全书内容驱动的规则

**源码证据**：[build-handbook.mjs](tools/build-handbook.mjs) 从 R13 样章生成器提取样式，并对 R07/R09/R12/R18 单独压缩段落和图表间距；[render-r13-review.mjs](tools/render-r13-review.mjs) 对表格和代码的屏幕、打印显示分别处理。

**判断边界**：可以确认全书样式依赖样章、存在章节专用间距补丁；不能据此宣称每页都挤压或溢出。实际断页、代码换行和图表可读性需在内容重构后渲染检查。

**修订**：建立按内容类型组织的全书样式，先减少信息混杂，再决定宽度、间距和分页。页数由合理覆盖决定，不能通过缩小字或临时紧缩个别章维持旧页数。

## 5 新的全书架构

### 5.1 保留知识领域，重新划定章与条目

保留七个知识领域作为主导航：语言基础、对象与资源、标准库、并发、组成与系统、网络、构建与调试。它们不是不可变的物理章数。章围绕一个稳定知识群；二级条目是具体对象或明确机制；三级条目承载接口组、操作或子规则。

```text
知识领域
└─ 知识群 / 章
   ├─ 类别总览与先修入口
   ├─ 具体对象 / 规则
   │  ├─ 定义、语法或公开声明
   │  ├─ 基础写法 / 构造与初始化
   │  ├─ 常用操作分组
   │  ├─ 短例、结果和关键条件
   │  └─ 机制与进阶规则
   └─ 组合应用、相关条目和来源
```

章前总览只交代分类、主要对象及阅读依赖，不重复每个对象的所有限制。章后综合应用不能替代各条目的基本写法。

### 5.2 优先调整的章节边界

- **R06**：语句、普通函数、lambda/可调用对象分成清楚的知识组；若展开后跨度过大，再拆为独立章。
- **R14**：有序关联、无序关联、适配器三个知识群独立导航，必要时拆章；不能让 map、哈希与优先队列共用一个笼统操作表。
- **R18**：文本转换/格式化与数值/随机/位操作分组；展开后优先拆章，避免持续增加同节主题。
- **R19**：建议拆为时间库、流与文件读写、文件系统三章；这三个领域的对象、使用过程和错误形式明显不同。
- **R23**：区分异步执行模型、队列与关闭机制、协程概念；线程池完整实现作为组合专题，基础入口不依赖阅读该实现。
- **R27**：现有从二进制到库使用的顺序基本可复用；把装载机制、库操作示例、ABI/插件进阶分层。

其余章也按清单决定拆分或合并。先确定条目数量和知识依赖，再生成新章号；旧 R 编号只作为迁移来源。所有来源条目都要有“保留、重写、补齐、拆分、迁移或删除”的明确去向。

### 5.3 两条阅读路径

**首次学习路径**：构建最小程序 → 类型与初始化 → 表达式和语句 → 函数、引用和基本生命周期 → 类与 RAII → 常用字符串/容器/算法 → 基本错误处理 → 线程与锁 → 系统、网络及工具入口。借用、失效和其他会影响当前写法正确性的条件随对象解释。

**工作查阅路径**：按类型/符号、语言概念、头文件、操作任务或工具命令进入相应条目，直接看语法/签名、参数结果、短例和条件。无需先读整个知识领域的长说明。

每章提供两至三行的先修提示。排序比较器的基础定义放在算法比较器条目，关联容器给局部约束与链接；迭代器的最低使用概念在容器首次遍历处简短引入，完整类别在迭代器章展开，避免来回跳转才能理解第一段。

### 5.4 内容深度与版本分开标记

阅读层级采用“基础操作、机制解释、进阶后查”；版本另标 C++17、C++20、C++23；系统条目另标平台。不要把“新版”自动当作“高阶”，也不要把“使用频率低”当作“可以不定义”。

常用对象独立展开；低频操作可集中为索引；复杂实现和生产责任进入专题。完整覆盖不等于逐个复制标准库所有重载，必须明确本书展开范围、只索引范围和范围外内容。

## 7 条目、正文和代码的新规则

### 7.1 四类条目模板

**语言规则**：名称与定义 → 语法形状 → 最常用写法 → 结果与成立条件 → 典型差异/错误 → 机制或例外 → 相关条目。初始化、运算符、函数、类、模板都适用，但不强制每项都有复杂反例。

**标准库类型/函数**：分类、用途、头文件与版本 → 公开声明摘要 → 模板参数或函数参数 → 构造/初始化（类型适用） → 常用接口分组 → 返回值、状态变化及条件 → 短例 → 相关机制。声明摘要明确省略哪些部分，不能伪装成标准完整定义。

**系统/协议机制**：实体定义与分类 → 工作过程/关系图 → 正常使用或交互 → 对应接口/报文/状态 → 关键条件 → 常见现象及调查入口。语言保证、常见实现、OS 保证、协议规则明确区别。

**工具/工程操作**：工具用途与适用环境 → 输入及准备 → 命令/操作 → 输出或可观察结果 → 常用参数 → 典型诊断 → 扩展入口。命令短例可用占位路径或相对文件名；实际机器核验信息在构建说明。

同一页只显示适用于该对象的字段。不要对所有条目强制添加复杂度、异常、平台、排障等空壳栏目。

### 7.2 接口展开到什么程度

常用接口至少让读者就地知道：名称和常用签名；参数是什么意思；返回什么或改变什么；怎样调用；必要的前提与失败情况。容器另交代复杂度和失效，锁另交代所有权/阻塞，系统调用另交代错误与清理。

重载按语义分组。一个操作因数量、范围、初始列表不同而改变含义，不能只列函数名；仅 cv/ref 等技术变化时可给摘要和扩展入口。类型相近时维护公共接口组，但每个具体类型仍有入口、差异和自己的基础短例。

“声明定义”按对象解释：语言实体讲声明/定义区别；标准库给公开声明与模板参数；使用代码给对象定义和初始化。除非讲实现机制，不展示整套标准库内部实现。

### 7.3 正文压缩办法

每段必须新增至少一种有用信息：定义、分类、语法/操作、结果、条件或机制解释。重复“工程上要注意”“不能假设”“应先检查”的泛泛提示，合并为对象对应的一条具体规则。

保留影响正确性的约束并紧贴写法；长实现差异移到机制层；跨章总论改为链接。删除对读者没有增量的复述、验证过程流水账、作者机器信息和不必要的道德式建议。不要预先承诺删去多少百分比，补全常用接口可能增加有效内容。

标题使用“基础类型”“声明与定义”“std::optional”“条件变量”“动态装载”“断点与单步”等名称。劝告式标题和否定式口号改为正文里的精确说明。

### 7.4 三层代码组织

1. **操作短例**：通常 3—12 个有效语句，集中展示一个写法；范围是目标，不是硬性删行要求。适当说明头文件、对象初始状态和结果。
2. **机制例**：只保留解释生命周期、所有权、状态或时序所需代码，常见约 10—30 行；配图或文字说明关键变化。
3. **组合应用**：可编译程序、线程队列、插件、解析器或小工程位于章末/配套源码；正文说明任务和阅读重点，核验包装不必全部贴出。

每个示例先写一句用途，再给代码，然后说明结果或状态。确定结果可写短注释；并发程序不承诺未规定的输出顺序；实现相关大小与地址明确说明环境；示意代码标为摘录或伪代码。代码说明不是逐行复述语法。

较长调用和重要语法使用代码块，避免藏在长行内代码中。若读者可直接粘贴运行，提供完整上下文；若展示多种可选初始化，分段或使用不同变量名，避免看似一段程序却重定义。

### 7.5 术语、数字与来源

首次出现术语给中文、必要英文/缩写和一句定义；后文回链到主要条目。基础类型的字节数、值域和位数区分标准要求与具体 ABI；数字给单位和适用环境，不用“实现决定”作为全部解释。

来源紧邻关键规则或条目末尾，避免每句都重复同一链接；版本、平台直接贴近结论。公开草案与网页核对不等于平台实际运行，编译成功也不替代标准语义核对。

适合保留的表：同类类型的性质对比、操作差异、复杂度、明确的失效规则、返回状态、工具命令映射。基础类型可以逐项查询，异常保证可以横向比较。

需要转换的表：阶段流程改为流程/时序图；一个对象的大量接口先按成员组拆开；一个单元格包含数个重载及长解释，拆成接口条目；知识综述改为简短定义和分类。不能把所有表都换成列表，也不能仅改表头而保持原有混杂。

### 8.2 表格字段按任务选择

| 表格用途 | 推荐字段 | 内容过多时的处理 |
| --- | --- | --- |
| 类型性质 | 类型、性质/范围、适用说明 | 按类型家族或 ABI 拆分 |
| 构造/初始化 | 形式、代码、得到的状态 | 不同语义类别分别解释 |
| 接口速查 | 接口、参数/结果摘要、条件 | 详细签名和例子放对应条目 |
| 操作影响 | 操作、状态变化、失效/复杂度 | 引用和迭代器维度过宽则拆表 |
| 工具命令 | 命令、用途、结果/适用范围 | 使用会话另列，不挤在单元格 |

首列应标明确实体，不强制所有表都叫“对象”。通常控制在 3—4 个有意义的列；需要更多列时先判断比较任务是否应拆分。短代码可以在表内，完整调用过程使用代码块。表前定义必要概念，表后只解释难以从表中读出的差异。

### 8.3 图的分工

- 分类图：回答有哪些对象及其关系。
- 结构图：回答对象、所有者、存储或资源怎样关联。
- 流程/时序图：回答构建、调用、锁等待、协议交互的顺序。
- 状态图：回答线程、future、连接或任务怎样改变状态。

每图只回答一个主要问题，使用已定义的名称。图与正文相互补充；纯文本已经足够的短清单无需强行画图。44 幅现有 SVG 按是否仍被引用、是否符合新结构逐幅保留、修改或删除，数量不作为完成指标。

### 8.4 建立真正的全书样式

将公共样式从 R13 专用渲染脚本中独立管理，样章与整书共用同一来源；屏幕与打印规则分别维护。内容类型使用统一样式，不按 R07/R09 等章号临时压间距。

以下是供样页试排的初始参数，最终以实际可读性确定：

- 屏幕正文保持约 15—16 px 和适当行宽；侧栏按篇/章导航，章内目录支持具体条目。
- A4 正文约 10.5—11 pt，代码和表格尽量不低于约 9 pt；选已有中文字体和等宽代码字体，字体缺失应检查替代结果。

### 8.5 HTML 与 PDF 分别验收

HTML：代码保留有意义的行结构，窄屏可以横向滚动；表格不能依赖无限宽视口；导航和链接可达，重要条目有稳定锚点。不能把窄屏的固定宽度策略直接作为打印方案。

PDF：标题与首段不孤立，表头续页重复，普通表行避免跨页；短代码尽量完整放置，长代码按逻辑段允许分页。代码换行由作者或排版规则控制，检查标识符、模板参数和命令没有被误导性折断。图中标签实际打印可读；不要强制整张巨大表或长程序不可分页而制造大块留白。

重排后重点检查篇章入口、密集接口页、宽表页、跨页代码、图注及索引。自动溢出检查发现的是候选问题，最终仍需查看实际页图。

## 10 全书实施顺序与 Agent 分工

### 10.1 阶段 A：内容盘点和结构冻结

主编辑负责全部 32 章及附录的条目清单：对象类别、展开深度、先修知识、关键操作、原位置、新位置、版本/平台、处理动作与验收点。183 个旧二级条目逐个映射，不是把旧标题直接当新条目；新增的基础操作也进入清单。

### 10.2 阶段 B：跨领域样例验证模板

### 10.3 阶段 C：覆盖全部章节的正文重构

按知识职责分批完成，顺序是语言/对象 → 标准库 → 并发/系统 → 网络/工程；有明确边界的任务可并行。每批同时处理内容、短代码、图表和来源，不能先把全部正文改完再统一补接口。

每批都检查：具体对象是否可查、常用操作是否完成、层级是否清楚、重复是否迁移、例子是否正确。保留有效已测内容，按新增或改变的代码验证；章节通过后再进入整合，不把“文件写完”作为完成条件。

## 附录 B 借鉴旧笔记时的技术校正

以下项目仅说明正式稿应怎样借鉴笔记，不修改用户原始笔记，也不把它们算成 v0.1 原稿的错误。

| 笔记中的写法或结论 | 正式稿采用的校正 | 核对依据 |
| --- | --- | --- |
| `vec.emplace(30)` 表示尾部原位添加 | 尾部用 emplace_back(30)；emplace 的首参数是位置 | [vector 接口](https://timsong-cpp.github.io/cppwp/n4659/vector.overview) |
| 未初始化的局部 array 整数元素默认全零；array.swap 交换底层指针 | 用 `{}` 展示零初始化；array.swap 逐元素交换，不是交换两根存储指针 | [array](https://timsong-cpp.github.io/cppwp/n4659/array) |
| `--list.begin()` 可以回到 end，并推断 end 内部存储 size | begin 不满足该递减操作的前提；不能依赖哨兵实现细节 | [双向迭代器要求](https://timsong-cpp.github.io/cppwp/n4659/bidirectional.iterators) |
| deque 被泛称为稳定容器；改用下标即可避免失效问题 | 元素引用与迭代器分开判断；下标也可能因插删改变逻辑身份 | [deque 修改规则](https://timsong-cpp.github.io/cppwp/n4659/deque.modifiers) |
| 节点句柄有 `release()`；stack/queue 的 `_Get_container()` 是 C++17 标准接口 | 不把这两个写法纳入可移植标准接口；节点句柄与适配器按公开标准接口展示 | [节点句柄](https://timsong-cpp.github.io/cppwp/n4659/container.node.overview)、[容器适配器](https://timsong-cpp.github.io/cppwp/n4659/container.adaptors) |
| mutex 头文件列出 recursive_lock、timed_lock、lock_gard | 分别校正为 recursive_mutex、timed_mutex、lock_guard；递归定时类型为 recursive_timed_mutex | [C++17 mutex 类型](https://timsong-cpp.github.io/cppwp/n4659/thread.mutex) |
| unique_lock&lt;mutex&gt; 调用 try_lock_for | 使用具备定时能力的互斥量，例如 timed_mutex | [unique_lock 锁定](https://timsong-cpp.github.io/cppwp/n4659/thread.lock.unique.locking) |
| condition_variable 用 `wait(lock, duration, pred)`，另有 chorono 拼写 | 定时相对等待用 wait_for；chrono 拼写及完整函数定义重新校验 | [条件变量](https://timsong-cpp.github.io/cppwp/n4659/thread.condition.condvar) |
| future.valid 在未就绪时返回 false；先同线程 get，再 set_value | valid 表示是否关联共享状态；未就绪仍可为 true；get 会阻塞，提供者须先设值或在其他执行路径设值 | [future](https://timsong-cpp.github.io/cppwp/n4659/futures.unique_future) |
| 默认 async 通常新建线程，作为可依赖行为 | 默认允许 async 或 deferred；需并发时明确策略 | [async](https://timsong-cpp.github.io/cppwp/n4659/futures.async) |

另外，重复变量名、未声明对象、错拼类型、全角分号等需在整理片段时消除。简洁范例必须有明确上下文，不能让读者把多个“可选写法”误当成一段可直接粘贴的程序。
