# C++ Reference Handbook 问题报告与改进方案

日期：2026-10-09。审查对象：v0.1，7 篇、32 章。状态：**分析与方案已形成，正文尚未按本报告修订**。

## 1 结论与目标

当前首稿与用户要求之间存在明显的编写方向偏差。它已经收集了许多规则、限制、工程建议和核验依据，却没有充分建立“类别 → 具体对象 → 声明与参数 → 构造与初始化 → 分组接口 → 简短用例 → 必要限制”的查阅结构。读者往往先看到提醒、复杂条件和综合程序，仍不清楚正在介绍什么，以及最基本的用法是什么。

改进需要重新组织条目，单独删几句话、换几个表头不足以解决问题。建议保留准确的规则与已有有效代码，把基础概念和常用接口放在入口，按对象补齐知识结构，再压缩重复说明。

用户需要的手册应同时做到：

1. **入门可读**：概念第一次出现就有简短定义；示例先说明用途；基础操作先于复杂例外。
2. **对象可查**：知道类型或符号名称，就能找到头文件、声明、初始化、常用函数及差异。
3. **代码专业而精简**：代码直接呈现写法与结果，必要注释贴近相关语句，避免把测试包装当作主要教学内容。
4. **分类清楚**：既有总分类，也有每个具体类型和接口组的稳定入口。
5. **信息具体**：类型的大小与范围、函数参数与返回值、操作条件等不能被“查文档”“视实现而定”替代。
6. **轻重明确**：必读、常用、进阶后查及版本扩展有一致标记。

用户所说的“废话多”，不宜解释成“边界规则都多余”。实际问题是大量正文用于提醒、否定和工程责任，基础条目却展开不足；同一限制又在正文、图注、综合例子、排障和索引中反复出现。应提高每段对当前对象的解释价值，保留真正影响使用的条件。

## 3 用户要求的准确整理

### 3.1 从两份笔记提取的组织要求

容器笔记的有用之处在于连续且可预测的层级：

```text
容器
├─ 顺序容器
│  ├─ std::vector
│  │  ├─ 头文件、声明与模板参数
│  │  ├─ 构造与初始化
│  │  ├─ 元素访问
│  │  ├─ 迭代与遍历
│  │  ├─ 大小与容量
│  │  └─ 插入、删除及其他操作
│  ├─ std::array
│  ├─ std::deque
│  ├─ std::list
│  └─ std::forward_list
├─ 有序关联容器：set / multiset / map / multimap
├─ 无序关联容器：unordered_set / unordered_multiset /
│                 unordered_map / unordered_multimap
└─ 容器适配器：stack / queue / priority_queue
```

同步笔记的优势是直接以 `std::mutex`、`std::lock_guard`、`std::unique_lock`、`std::condition_variable` 等符号作为入口，再给锁定、延迟锁定、尝试锁定、等待和通知的短代码。用户无需先读一整段工程背景才能定位操作。

“声明定义”在不同对象中应分别处理：语言条目解释声明与定义的区别；标准库条目提供公开声明摘要和模板参数；使用示例展示对象定义与初始化。除非在讲实现原理，不应要求展示完整标准库实现源码。

### 3.2 必须避免的误解

- “专业”意味着名称准确、维度统一、规则具体；不等于增加术语或把表格写成压缩长段。
- “简洁”意味着一次只解释一个主要对象或操作；不等于省掉头文件、上下文和有效性条件。
- “详细”意味着常用类型和操作有完整查阅位置；不等于在每节重复所有异常与生产场景。
- “入门”仍需保证准确，但首次路径只展开理解当前操作所需的规则。
- “像 cppreference”应落实到分类、声明、成员分组、版本和语义；只添加 cppreference 链接无法满足要求。

## 5 已确认的系统性问题

问题优先级：P0 为影响手册定位的结构问题；P1 为影响入门和常用查阅的问题；P2 为编辑收尾问题。这里的“待修订”表示报告提出了行动，并不表示修改已经完成。

### P0-01：对象组织弱于工程提醒，检索主体不稳定

**证据**：R01 的声明表以写法开头；R03 的初始化表同样如此。R14 用“有序关系与哈希契约”“查找、插入与更新”等机制分节，map/set/multi/unordered 类型主要挤在总表；用户很难直接进入某一个类型的完整条目。R21 第一节以锁所有权为主题，多种锁包装器只有横向速查。

**影响**：读者无法稳定回答“我现在查的是哪个对象”“这个类型还有哪些常用操作”。常用函数被介绍，却不构成完整接口地图。

**原因判断**：从原稿可推断，编写更重视防误用、边界和生产责任，未把对象目录当作首要组织骨架。此处是对成稿的编辑分析，不是对当时编写过程的事实记录。

**方案**：对象分类与具体类型条目作为主线；跨类型比较表作总览；机制、差异和排障放在已有对象条目之后。每个类型在正文和索引中都有明确落点。

### P0-02：标准库常用覆盖不足且不均衡

**证据**：R13 对 vector 较详细，array 主要在选型表和一个初始化片段中，deque、list、forward_list 重点讲失效/位置契约。R14 部分类型以合并名称甚至 `unordered_multi…` 表示。R21 没有 recursive_mutex、timed_mutex、recursive_timed_mutex 的独立说明，recursive_mutex 只在排障中作为提醒出现。

**影响**：选型与高级规则篇幅充足，日常查初始化、遍历、成员操作时仍需另找资料。标题和附录覆盖一个符号，不等于其正文条目已完整。

**方案**：建立类型及高频接口清单，逐项填写“已覆盖位置 / 缺少字段 / 计划落点”。基础类型与常用接口齐备后，再决定低频重载是否展开。完整性以查阅任务验收，不以页数、章节数或引用数验收。

### P1-01：基本概念已有名称，却没有足够的解释入口

**证据**：ODR 已有中文名称，但紧接着出现 odr-use 等术语；R02 概念与对象表示密度很高；R21 在逐项解释锁类型之前就进入不变量、关闭与背压。

**影响**：读者需要同时掌握多个先修概念才能理解一个基础结论。

**方案**：首次出现采用“全称/名称 + 一句定义 + 最短对照例”；进阶例外通过等级和明确入口承接。基本概念不能仅靠末尾标准链接解释。

### P1-02：表格职责混杂，单元格内容不适合横向比较

**证据**：R01 将声明、定义、链接组织放在同表；R02 基础类型用场景和限制替代具体属性；R03 以语法起列并合并不同类别；placement new 的先后步骤压成表格。

**影响**：行的身份不清，列的维度不统一，读者需要把表格重新读成长段正文。

**方案**：概念表第一列用名称，接口表第一列用函数符号，比较表首列用比较对象；流程用图或编号。函数名本身就是被查阅的对象，因此接口表以 `reserve` 起列合理，不能机械规定所有表格第一列都必须是中文。一般使用 3—5 列，过长条件在条目中展开。

### P1-03：示例重核验，教学单元过大

**证据**：R01 首例有失败分支、退出码脚本及溢出限制；R02 一段完整程序混合两种机制和析构计数；R21 主要完整例子是带关闭语义的有界队列。

**影响**：测试控制流、异常处理和多个设施遮住了当前要学的表达式。完整程序正确并不自动说明它适合作为第一例。

**方案**：正文优先短片段；每段给用途、前提和结果。完整可运行程序用于组合实践或配套验证，保留输出与失败检查。基础用法、机制图、工程组合例分层，不把验证脚本逐节嵌入正文。

### P1-04：反复提醒占用了基础资料的篇幅

**证据**：R13 的失效、稳定身份、生命周期及性能提醒分布在多个条目、图注、工作排障与章末导航；R20/R21 对超时不等于取消、关闭后仍需等待等说明多处出现。多数结论有价值，但重复组织增加阅读成本。

**方案**：删除空泛劝告；同一规则设唯一主要解释位置。其他位置仅保留一句当前操作所必需的限制，必要时链接具体条目。把“不会自动……”改成可操作的条件，例如直接写“wait 的谓词读取和修改使用同一 mutex”。不能为追求短而删掉空容器访问条件或失效范围。

### P1-05：本机核验信息混入面向读者的正文

**证据**：R01 的绝对工具路径、QA 目录和 PowerShell 检查；多章对 Windows GCC 10.3 实测范围的叙述；README 同时承担本机状态与阅读入口。

**方案**：正文保留语言版本、必需头文件及接口的平台条件；工具条目保留常用命令。作者机器路径、核验脚本、实测结果维护在现有 BUILD-NOTES/SAMPLE-NOTES。正文中涉及实现的结论仍须就地注明适用范围。

### P1-06：信息分层存在，但就地标记不足

**证据**：多数章首说明首次读哪几节，但节标题没有统一等级，混合节内部更无差别。placement new、类型性质与基本类型连续出现，对新读者几乎同等醒目。

**方案**：章首给短阅读顺序，具体对象旁给等级。标记主要对象和真正存在不同学习要求的子条目，不给每一段都加徽标。

### P2-01：标题与来源展示降低了专业查阅感

**证据**：R02 的评价式标题、R20 的提问式标题、R22 的判断式标题；多节结尾是多个链接名词加句号。

**方案**：标题使用主题名与必要限定，如“基础类型”“std::thread”“条件变量”“原子操作与内存序”。解释性观点保留在正文。来源集中在条目/章节资料区；有阅读价值的交叉引用写清跳转目的。

### 6.1 保留的内容

### 6.3 建议目录

保留 R13、R14 稳定编号，先调整章内结构；不以增加章节数量作为修复目标。

- R13：顺序容器概览 → vector → array → deque → list → forward_list → 跨类型复杂度与失效对照。
- R14：关联容器分类 → set → multiset → map → multimap → 四种无序关联容器 → 三种容器适配器 → 跨类型对照。
- 每个对象使用三级标题组织构造、访问、迭代、容量、修改、专用操作及关键条件。

- C++20/23 扩展置于明确的版本条目；不把 C++26 类型引入本轮核心覆盖。

### 6.4 vector 条目示范

以下展示改写方向，属于方案中的正文片段，未替换原章。

**std::vector — 常用；基础操作必读。** 头文件 `<vector>`。一般 `vector<T>` 是可变长度、连续存储的序列，适合下标访问、遍历和尾部追加。`vector<bool>` 的特化另查。

公开声明摘要，省略类体：

```cpp
namespace std {
template<class T, class Allocator = allocator<T>>
class vector;
}
```

`T` 为元素类型，`Allocator` 为存储分配器，初学使用默认值。声明摘要展示模板形状，实际使用包含头文件，不自行补写标准库声明。操作对 `T` 的要求随构造、插入、赋值等不同；分配器细节归进阶条目。[C++17 vector 声明与接口](https://timsong-cpp.github.io/cppwp/n4659/vector.overview)。

**构造与初始化**：下面是 C++17 局部片段，需包含 `<vector>`；各变量名称独立。

```cpp
std::vector<int> empty;                 // 空序列
std::vector<int> zeros(3);              // {0, 0, 0}
std::vector<int> repeated(3, 7);         // {7, 7, 7}
std::vector<int> listed{3, 7};           // {3, 7}
std::vector<int> copied(listed);        // 拷贝 {3, 7}
std::vector<int> range(listed.begin(), listed.end()); // {3, 7}
```

初始化完成后才介绍操作，不把 assign 写成构造：assign 替换已经存在的容器内容。

**接口分组**：

| 组 | 常用对象 | 本组必须解释的内容 |
| --- | --- | --- |
| 元素访问 | operator[]、at、front、back、data | 参数/返回类型、下标范围、空容器条件、const 重载 |
| 迭代与遍历 | begin/end、cbegin/cend、rbegin/rend | 半开区间、尾后位置、引用与值遍历 |
| 大小与容量 | empty、size、max_size、capacity、reserve、resize、shrink_to_fit | 长度与容量区别、元素是否创建/销毁、缩容请求的性质 |
| 修改 | assign、push_back、emplace_back、insert、emplace、erase、pop_back、clear、swap | 位置参数、返回值、成功后内容变化与失效 |

每组中的重要函数再给短签名和短例。以 reserve 为例：

```cpp
void reserve(size_type new_capacity); // 成员声明摘要
```

`new_capacity` 请求至少能容纳的元素数；函数返回 void。成功调用不改变 size，发生重分配会使旧元素的指针、引用、迭代器失效。完整容量条件、复杂度与异常保证在同一条目展开；需要调整元素数时链接 resize。

片段需包含 `<vector>`；结果不依赖实际增长倍率：

```cpp
std::vector<int> v{10, 20};
v.reserve(8);             // size == 2；capacity >= 8
v.resize(4, -1);          // {10, 20, -1, -1}
```

失效矩阵仍保留，但放在修改接口之后。接口已知时，矩阵才有明确查阅对象。[C++17 容量规则](https://timsong-cpp.github.io/cppwp/n4659/vector.capacity)。

### 7.2 具体差距

- R20 已解释 thread、future、promise、packaged_task、async 和 jthread，但缺少按各对象完整分组的基本操作示范。promise 主要在提供者表中，读者不容易直接找到一条完整的 set_value/get 路径。
- R21 已解释 mutex、RAII 锁、谓词等待与共享锁，但 timed/recursive 互斥量缺系统条目，锁标签和多锁函数缺独立操作入口。
- R21 的有界队列是有效的组合例；应在基础锁、等待和通知的短例之后，归为应用组合或进阶，不能代替各设施的基本示例。
- R22 对 atomic 的操作有文字说明，内存序和发布用较大篇幅；需要先给 load/store/exchange/fetch_add/CAS 的分组清单。atomic_flag 在附录出现，正文没有独立操作条目。
- 现稿的等待、取消、关闭规则应继续保留，并在 R20—R23 间确定主要解释位置，减少重复长段。

### 7.3 unique_lock 与超时锁定示范

对象条目先解释：`std::unique_lock<Mutex>` 管理一把互斥量的所有权，可延迟、尝试和提前释放；它的可用操作取决于 Mutex 提供的能力。

下列 C++17 局部片段需包含 `<mutex>`、`<chrono>`，展示“尝试在等待期限内取得 timed_mutex”。超时函数不承诺程序实际返回时间有严格上界。

```cpp
std::timed_mutex m;
std::unique_lock<std::timed_mutex> lock(m, std::defer_lock);
if (lock.try_lock_for(std::chrono::milliseconds(100))) {
    // 此分支持有 m；作用域退出时自动释放。
} else {
    // 未取得锁，不访问由 m 保护的状态。
}
```

该短例清楚表达类型、构造、参数、返回 bool 和分支条件。基础 lock_guard 可用更短的作用域例；条件变量则给共享状态、wait 谓词和通知双方，图专门说明释放锁、等待和重新取得锁的关系。[C++17 unique_lock 锁定要求](https://timsong-cpp.github.io/cppwp/n4659/thread.lock.unique.locking)。

## 8 全书编写规范的具体改进

### 8.1 对象条目模板

模板用于检查必需信息，不要求每项都成为单独小节。

**语言条目**：名称与等级 → 一句定义 → 语法/声明 → 基本规则 → 一个短例与结果 → 当前最重要的错误 → 进阶条件 → 来源。

**标准库类型条目**：全限定符号 → 头文件/最低版本/用途 → 声明摘要及模板参数 → 关键成员类型 → 构造与初始化 → 成员按职责分组 → 典型短例 → 复杂度/失效/异常 → 同族差异与来源。

**标准库函数条目**：函数符号 → 常用签名或明确的简化签名 → 参数意义 → 返回值 → 前置条件及副作用 → 短例 → 复杂度、失效或错误 → 版本差异。注明省略的重载，不把返回值藏在长段里。

**系统机制条目**：机制名称 → 所处层级和平台 → 构成/状态/调用过程 → 简洁关系图 → 常用接口及结果 → 必要限制。系统主题不用硬套标准库成员表。

### 8.2 两个维度的标记

| 维度 | 标记 | 含义 |
| --- | --- | --- |
| 使用频率 | 常用 / 特定场景 | 相对本书入门与常见开发任务判断，不冒充统计数据 |
| 学习要求 | 基础必读 / 进阶后查 | 初次学习需要理解，或遇到相关任务再深入 |

例如：vector 基础接口为“常用 · 基础必读”；迭代器失效为“常用 · 基础必读”；placement new 为“特定场景 · 进阶后查”；复杂原子协议和回收为“特定场景 · 进阶后查”。等级不等于价值高低，也不表示高级错误可忽略。

**语言版本另标**，如“C++20”，不得当作“进阶”的同义词。一个入门常用接口也可能要求较新标准。

### 8.3 表格与图的分工

| 内容关系 | 首选形式 | 示例 |
| --- | --- | --- |
| 对象的属性比较 | 表格 | 类型大小、容器能力、锁工具差异 |
| 函数的接口说明 | 小表 + 代码 | reserve 的参数、返回值和条件 |
| 先后步骤、状态变化 | 流程图或编号步骤 | 预处理到链接、对象槽位重用 |
| 内存与地址关系 | 结构图 | size/capacity、节点与连续存储 |
| 线程间等待和同步 | 时序图 | condition_variable、发布关系 |
| 一条规则或单一写法 | 短段或代码 | 默认构造、访问一个元素 |

R01 的声明/定义表可以改成：

| 对象或类别 | 写法 | 含义 |
| --- | --- | --- |
| 函数声明 | `int f(int);` | 声明函数名称及参数、返回类型，不提供函数体 |
| 函数定义 | `int f(int x) { return x; }` | 提供函数体；函数定义也是声明 |
| 变量声明，非定义 | `extern int count;` | 声明已有外部变量，本语句不定义它 |
| 变量定义 | `int count = 0;` | 定义并初始化变量，此例用于命名空间作用域 |

链接属性另表说明。“函数定义也是声明”须保留，以免改表后制造二者互斥的错误模型。[C++17 定义与 ODR](https://timsong-cpp.github.io/cppwp/n4659/basic.def.odr)。

R03 可先用以下表说明普通自动局部 int 的形式。语法类别与其触发的初始化过程并不总是互斥：

| 初始化类别 | 写法 | 本例结果 |
| --- | --- | --- |
| 默认初始化 | `int n;` | 未初始化为确定值；不可直接读取 |
| 值初始化，此处由空列表触发 | `int n{};` | 值为 0；语法是直接列表初始化 |
| 直接初始化 | `int n(3);` | 值为 3 |
| 拷贝初始化 | `int n = 3;` | 值为 3 |
| 直接列表初始化 | `int n{3};` | 值为 3，受列表窄化规则约束 |
| 拷贝列表初始化 | `int n = {3};` | 值为 3，受列表窄化规则约束 |

这里各行是独立写法，不组成一个作用域中的程序。再说明 `int n{};` 是空列表形式，对该 int 产生值初始化；类类型还需按聚合、构造与列表规则判断。聚合初始化、零初始化等单独解释，不把所有 `T x{};` 无条件归为同一过程。[C++17 初始化](https://timsong-cpp.github.io/cppwp/n4659/dcl.init)、[列表初始化](https://timsong-cpp.github.io/cppwp/n4659/dcl.init.list)。

### 8.4 基础类型资料必须具体

拆分整数、浮点、字符与其他基础类型；枚举移到用户定义类型条目。每个具体类型逐行给出大小、位数和范围所需信息。

建议至少提供两层资料：

1. 标准约束：字节与位的区别、类型大小关系、最低范围、实现定义属性。
2. 明确标注平台/ABI的实例：具体字节数、位数、实际范围；同时给 `sizeof`、`CHAR_BIT` 和 numeric_limits 的查询例。

例如下表只表示 Microsoft 文档描述的 MSVC 数据模型，不能作为 C++ 跨平台保证：

| 类型 | 字节数 | 位数，8位字节 | 数值范围 |
| --- | --- | --- | --- |
| int | 4 | 32 | −2,147,483,648 至 2,147,483,647 |
| unsigned int | 4 | 32 | 0 至 4,294,967,295 |
| long | 4 | 32 | −2,147,483,648 至 2,147,483,647 |
| long long | 8 | 64 | −9,223,372,036,854,775,808 至 9,223,372,036,854,775,807 |

正式重写还须补足其他类型和已核对的另一种常见数据模型，不能把本示范的四行视作完成类型表。若采用 LP64，对 long 与指针等差异明确列出，并核对目标 ABI。尤其避免把“64位系统”直接当成 long 为64位的依据。[MSVC 类型范围](https://learn.microsoft.com/en-us/cpp/cpp/data-type-ranges?view=msvc-170)、[C++17 基础类型约束](https://timsong-cpp.github.io/cppwp/n4659/basic.fundamental)。

浮点表须分别给出最低有限值、最大有限值、最小正正规值和精度；`numeric_limits<float>::min()` 不是最负值，最负有限值查 `lowest()`。正式表不得把浮点范围写成整数区间。[numeric_limits 成员定义](https://timsong-cpp.github.io/cppwp/n4659/numeric.limits.members)。

### 8.5 存储与构建：补基础图，不混层级

存储说明至少分两幅图：语言层的作用域/存储期/生命周期关系；实现层的常见进程地址空间。实现图可包含代码、只读数据、已初始化数据、零初始化数据、堆、映射区及线程栈，但应说明区域名称、地址顺序与增长方向依平台而变。R02 给概览，R25/R27 承担细节，不把常见 `.bss` 布局描述成所有静态对象的语言保证。

构建阶段建议示意：

```text
源文件与头文件
    ↓ 预处理：包含、宏、条件编译
预处理结果
    ↓ 编译
汇编代码
    ↓ 汇编
目标文件 + 所需库
    ↓ 链接

```

这是 GCC 常用工具阶段图，中间文件可以不落盘，不能当作标准翻译阶段逐项等价图。GCC 工具条目解释 `-E`、`-S`、`-c`、`-o`，再解释常用 `-std`、警告、调试和优化选项；作者本机绝对路径不进入正文。[GCC 阶段与输出选项](https://gcc.gnu.org/onlinedocs/gcc/Overall-Options.html)。

### 8.6 GDB 前置入口

## 9 旧笔记的技术校正边界

以下项目仅说明正式稿应怎样借鉴笔记，不修改用户原始笔记，也不把它们算成 v0.1 原稿的错误。

| 笔记中的写法或结论 | 正式稿采用的校正 | 核对依据 |
| --- | --- | --- |
| `vec.emplace(30)` 表示尾部原位添加 | 尾部用 emplace_back(30)；emplace 的首参数是位置 | [vector 接口](https://timsong-cpp.github.io/cppwp/n4659/vector.overview) |
| 未初始化的局部 array 整数元素默认全零；array.swap 交换底层指针 | 用 `{}` 展示零初始化；array.swap 逐元素交换，不是交换两根存储指针 | [array](https://timsong-cpp.github.io/cppwp/n4659/array) |
| `--list.begin()` 可以回到 end，并推断 end 内部存储 size | begin 不满足该递减操作的前提；不能依赖哨兵实现细节 | [双向迭代器要求](https://timsong-cpp.github.io/cppwp/n4659/bidirectional.iterators) |
| deque 被泛称为稳定容器；改用下标即可避免失效问题 | 元素引用与迭代器分开判断；下标也可能因插删改变逻辑身份 | [deque 修改规则](https://timsong-cpp.github.io/cppwp/n4659/deque.modifiers) |
| 节点句柄有 `release()`；stack/queue 的 `_Get_container()` 是 C++17 标准接口 | 不把这两个写法纳入可移植标准接口；节点句柄与适配器按公开标准接口展示 | [节点句柄](https://timsong-cpp.github.io/cppwp/n4659/container.node.overview)、[容器适配器](https://timsong-cpp.github.io/cppwp/n4659/container.adaptors) |
| mutex 头文件列出 recursive_lock、timed_lock、lock_gard | 分别校正为 recursive_mutex、timed_mutex、lock_guard；递归定时类型为 recursive_timed_mutex | [C++17 mutex 类型](https://timsong-cpp.github.io/cppwp/n4659/thread.mutex) |
| unique_lock&lt;mutex&gt; 调用 try_lock_for | 使用具备定时能力的互斥量，例如 timed_mutex | [unique_lock 锁定](https://timsong-cpp.github.io/cppwp/n4659/thread.lock.unique.locking) |
| condition_variable 用 `wait(lock, duration, pred)`，另有 chorono 拼写 | 定时相对等待用 wait_for；chrono 拼写及完整函数定义重新校验 | [条件变量](https://timsong-cpp.github.io/cppwp/n4659/thread.condition.condvar) |
| future.valid 在未就绪时返回 false；先同线程 get，再 set_value | valid 表示是否关联共享状态；未就绪仍可为 true；get 会阻塞，提供者须先设值或在其他执行路径设值 | [future](https://timsong-cpp.github.io/cppwp/n4659/futures.unique_future) |
| 默认 async 通常新建线程，作为可依赖行为 | 默认允许 async 或 deferred；需并发时明确策略 | [async](https://timsong-cpp.github.io/cppwp/n4659/futures.async) |

另外，重复变量名、未声明对象、错拼类型、全角分号等需在整理片段时消除。简洁范例必须有明确上下文，不能让读者把多个“可选写法”误当成一段可直接粘贴的程序。
