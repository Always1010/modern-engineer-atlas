# 写在前面

软件工程师交付的对象可以是一个库、一项在线服务、一台仪器、一套生产测试系统，或者运行在设备中的长期软件。它们会共同遇到数据、时间、资源和失败，却有不同的完成条件。一个测试工位把数值显示出来，还没有证明产品合格；一个服务返回成功，还需要解释故障后状态是否保留；一个固件能在开发板上运行，也还没有完成制造、更新与现场维护。

本书以现代 C++ 与系统机制作为共同基础，按照工作对象和产品责任进入各个方向。语言、操作系统、网络与框架不是彼此独立的技术清单：缓冲区复用会牵动对象生命期和 DMA；一次标定会连接仪器、估计、参数版本与工件身份；远端报工超时会把桌面界面带到持久化、幂等和质量放行的边界。理解这些联系，才能判断一个问题属于哪一层，以及需要与谁共同解决。

“能力地图”有三个层次。首先准确描述概念和对象，知道术语所指；其次解释机制与条件，知道某项保证在哪里结束；最后把结论落到可以检查的证据，例如契约、时间线、波形、发布清单、测量记录和恢复结果。书中的诊断和面试追问围绕这些层次展开，答案应能继续回答“为什么”“失败时怎样”“如何确认”，不要求背诵一个脱离条件的唯一方案。

## 共同基础怎样进入产品工作

全书保留十三篇、五十八章的稳定章号。第一至四章建立约束、数据、算法与协议的共同语言；第五至二十章解释程序、机器、C++ 语义、并发和性能；第二十一至二十七章把设计接到构建、验证、安全、交付和运行。后半部分按产品领域展开，最后两章把工作重新组织为可解释、可核查的能力证据。

这些内容不要求依次学完才允许开始项目。面对一个具体任务，先理解它的输入、输出、责任人与失败后果，再返回承担关键保证的基础章节。负责设备上位机的读者可能先需要第十九章的异步生命期、第二十五章的设计边界和第三十一章的事件模型；负责存储引擎的读者则要更早进入第六章的地址空间、第三十五章的持久化和第三十六章的事务。相同的 C++ 语法会参与不同的契约。

初学者可以先阅读第一至四章、第七章，以及第九、十四、十六、二十二、二十三章中的基本部分，再选择一条与工作接近的产品线。模板深层规则、无锁回收和具体 GPU 优化不应成为每个人的入门门槛。有经验的读者可以从交付或故障进入，但需要检查自己的结论依赖了哪一层保证：CPU 缓存一致性不能使 C++ 数据竞争合法，通信成功不等于设备动作完成，网页显示结果也不等于结果已经持久保存。

## 嵌入式产品从样机走向长期运行

嵌入式软件是产品中的一部分，其责任与传感、通信、供电、执行和制造方式相连。MCU 固件、RTOS 应用、Embedded Linux、异构实时系统并不是依照难度排列的升级阶梯。它们分别承担不同的资源、实时性、应用复杂度和维护要求，同一产品也可能同时使用几种平台。

第二十八章从芯片、板卡、元器件和电气边界出发，接到启动、总线、DMA 与调试。这里不仅需要看代码，还要能选择测量工具、辨认测量对象，并知道工具本身会怎样影响证据。万用表的一个数值、示波器的一段波形、逻辑分析仪的解码与调试器的处理器状态，各自只覆盖问题的一部分。具体操作限定在手册允许、隔离且能量受控的低压目标；现场高压、电池大电流与运动机构需要另行具备的专业程序。

第二十九章把 IRQ、任务、缓冲、截止期与功耗放回设备的工作周期，并继续走到烧录、标定、生产放行、更新和退役。第三十章在内核机制之外，解释板级支持、启动链、设备描述、系统镜像与用户态应用怎样组成 Embedded Linux 产品。Linux 与实时核并存时，通信通了只是第一步，二者的启动、共享数据、版本配对和失效恢复也需要共同设计。工业网络的时间和容量约束继续阅读第三十二章；机器人传感与控制接入第四十八至五十二章。

这些章节共享一条判断路线：识别硬件与软件版本，说明必须维持的不变量，收集能区分假设的证据，完成局部实现，再验证制造和现场条件。防呆、治具、烧录、标定、良率和追溯不是附在软件之后的名词，它们会反过来影响接口、存储布局、测试点、版本管理与诊断能力。

## 工业上位机从连接设备走向生产任务

上位机是相对于受控设备的位置描述，不代表固定的软件架构。研发调试工具关注快速观察和受控写入；标定系统关注参考输入、原始测量、参数与复测；产线测试站关注每件工件的测试计划、有效结果和放行；DAQ、HMI 与 SCADA 则分别强调数据采集、操作界面、监督监控及相关历史和告警。它们可以共用通信与界面机制，但成功条件不同。

第三十一章先建立 Windows 与 Qt 的对象、事件和线程边界，再把这些机制分配给工业应用责任。设备会话、测试流程、测量判定、结果存储与界面模型各有权威，不能因为同在一个进程就混成一个按钮回调。连接 PLC 时要区分工位握手与安全控制；连接 MES 时要区分生产执行事实与业务系统的确认。一个绿色 PASS 指示灯应该有精确含义，而不是模糊地代表所有事情都已完成。

第五十八章的设备项目沿一件低功耗节点的生产测试与标定展开：核对工件身份和计划版本，执行受控步骤，保存原始测量与判据，形成不可混淆的测试尝试，再同步生产结果。设备已执行而回包丢失、电脑在记录后崩溃、MES 接收后应答丢失，分别落在不同恢复边界。协议回看第四章，设计原则回看第二十五章，本地持久化回看第三十五章，幂等与消息恢复回看第三十四章。这样的连接使共同机制服务于生产任务，也避免再造一套重复的基础教程。

## 其他产品方向有自己的约束

在线服务、存储与数据产品见第三十三至三十七章。这里的主线是请求在部分失败、持久化、复制、事务和查询之间怎样保持约定；运行责任回看第二十七章。不能将单机内的对象寿命直接推广为跨进程一致性，也不能把一个去重键当成全部业务恢复协议。

音视频、图形与交互产品见第三十八至四十章。读者需要把时间、质量、延迟与资源预算同时放进分析，区分一帧内部的计算与完整交互链；相关数值基础在第一章，性能实验在第二十章。编译工具链和开发工具见第四十一、四十二章，重点是语言表示、优化合法性、运行边界和开发者可用的证据。

科学计算、GPU 与模型基础设施见第四十三至四十七章。先明确数值契约、设备执行和数据移动，再解释并行优化、算子、训练、推理与服务容量。一个核函数更快，不自动等于完整服务更快。机器人与自主系统可先读第五十二章的风险边界，再按第四十八至五十一章理解传感、通信、估计和控制，最后回到风险与验证证据。

大模型应用与 Agent 工程见第五十三至五十六章。模型接口、检索、工具执行与评估具有不同的权限和结果契约，不要求把每个应用都变成多 Agent 系统。无论最终选择哪个方向，第五十七章的面试链都用于检查解释的深度，第五十八章的综合项目都用于理解交付证据应怎样组织。

## 设计原则贯穿这些工作

第二十五章把设计原则和模式放在具体变化中理解。职责分离需要说明哪些原因会让模块变化；可替换性需要核对行为、失败和时序；依赖反转需要保护真正稳定的规则。工厂、策略、状态、观察者、适配器等模式是组织这些关系的手段，不能仅凭用了哪些类来证明设计正确。

读者可以带着三个问题回看每个方向：新增产品型号时需要改哪里，某个依赖失败时哪个承诺仍然成立，以及新的执行者能否接着解释旧状态。模式只有帮助这些问题变得清楚时才值得引入。语言选择、运行时多态和编译期策略也应服从资源、兼容和团队成本，而不是为了展示技巧。

## 如何理解版本 示例与来源

C++20 是本书的主要语言基线；C++23 补充与 C++26 前沿单独说明。前沿内容使用固定草案和核验日期，不把滚动网页中的新规则反向套到旧版本。Linux、Windows、CUDA、ROS、数据库和 AI 框架按章内给出的版本与适用条件理解，教材的参照版本不等于当前部署推荐。

本书区分四类材料：规范或官方产品文档所承诺的机制，企业或项目公开说明的实际实践，本书自行设计的教学系统，以及真正经过执行的实验结果。前两类应保留来源和限定条件，第三类帮助展开推理，不能冒充任何企业的真实内部实现。本版没有对教学技术代码进行编译执行，也没有完成真实硬件、在线 API、训练或性能实验；书中的自造日志、状态与数值均不是现场观测数据。

原创机制图帮助理解关系和边界；有明确许可的真实照片帮助辨认板卡、器件和仪器。照片中的接线、读数和波形没有自动成为本书实验的证据，不能依据外观直接复现操作。图注的署名与许可只适用于相应图片，不表示厂商认可本书，也不改变其他内容的权利状态。

各章保留来源入口。PDF 提供固定版式、目录与书签；EPUB 会随阅读器和字号重排；Markdown 适合检索与复制代码。读者应以相同发行版本的文件配套阅读，实际复现时再核对自己的编译器、依赖、设备、负载和权限条件。
