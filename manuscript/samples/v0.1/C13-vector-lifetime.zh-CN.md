# C13 样章 从一次扩容理解 vector 的边界

版本：样章 v0.1 · 卷一 共享基础 · 资料核验：2026-10-03 · 状态：编辑评审稿

所属章：C13 标准库容器算法与分配。重点覆盖 C13.02，并连接 C13.03 的失效规则、C13.04 的非拥有视图。本文先讲使用边界与视图，再回看迁移机制；小节编号沿用全书目录。本文不是 C13 全章；分配器、多态内存资源（PMR）及完整算法体系另写。

主线采用 C++20，公开规范参照的版本身份见 [S2]。全部代码均为原创教学示例，本版没有编译、执行或测量；文中“应当”“将会”描述规范推理或明确假设，不是运行记录。本文讨论通常的 `std::vector<T>`，不把 `vector<bool>` 的特化当作连续 `bool` 数组。

## 先带着一个故障来读

你在写设备日志查看器。接收模块把解码后的记录放进 `vector`，界面保存第一条记录的地址，打算稍后显示。小文件看起来正常，大文件偶尔出现乱码。接收模块没有主动删除第一条记录，为什么它的地址还是不能用了？

先别急着把容器换掉。真正缺失的信息是：界面拿到的是“记录的身份”，还是“记录此刻所处的位置”？当容器为了继续增长而更换存储区时，这两件事就会分开。

读完后，你应能完成三件事：判断一个地址能否跨过某次修改继续使用；解释预留容量对正确性和性能各能保证什么；为延迟消费的数据选择清楚的所有权方案。会调用 `push_back` 是起点，能写出这些边界才是本章的出口。

**先修小桥。** 你只需会函数、循环、数组和基本类。指针记录地址；引用给已有对象起另一个名字；迭代器是容器提供的位置访问接口。对象有生命周期，存储字节还在不代表那个对象还允许被访问。“未定义行为”表示程序违反了语言或库的要求，标准不再规定结果；它不等于“一定崩溃”。移动构造与异常保证在后面的进阶段补充，不妨先读到借用边界。

## C13.02 先分清元素与容量

想象一排可容纳记录的格子。`size()` 回答已有多少个元素，`capacity()` 回答当前存储安排在不重新分配的情况下能够容纳多少个元素。格子的比喻只帮助区分数量，它不是标准要求的对象内部布局。[S1][S3]

有了空间不等于有了元素：对一个空 `vector<int>` 调用 `reserve(100)`，不能接着写 `v[0] = 7`。如果你想得到 100 个可以按下标访问的元素，应按需求构造它们，例如 `resize(100)`；如果你想边解析边增加实际记录，应使用 `push_back` 或适当的插入操作。把这两种需求混在一起，既可能越界，也可能多做无用的初始化。

图 C13-A 读元素数量，也要读地址有效期。容量 6 和 10 只是示意数值，不是增长公式；图不规定 vector 对象内有几个指针，也不规定元素迁移的具体先后。

下面的例子故意使一次成功的 `reserve` 必须重新分配，而不猜测初始容量是否刚好等于 2。

```cpp
// C++20 教学示例；未编译、未执行。
#include <vector>

int main() {
    std::vector<int> samples{10, 20};
    const int* first = &samples[0];
    const auto old_capacity = samples.capacity();

    if (old_capacity == samples.max_size()) return 0;
    samples.reserve(old_capacity + 1); // 成功返回时重新分配

    // int value = *first; // 错误示意：不要执行这一行
    const int value = samples[0]; // 从容器重新取得当前元素
    return value == 10 ? 0 : 1;
}
```

这里没有输出乱码来“证明”错误。证明来自接口约定：成功增长容量后，旧元素地址失效。[S1] 重新读取 `samples[0]` 有效，是因为元素序列还包含值 10，不是因为 `first` 自动更新了。这个程序也可能在申请内存时抛出异常；“成功返回”这一前提不能省略。

回到日志查看器。若界面只保存下标，并在稍后通过仍存活的容器访问，重新分配本身不会改变下标含义。但删除、插入和排序可能改变“第零条是谁”。需要跨编辑操作追踪业务记录时，应保存稳定记录 ID，再查找当前记录。下标解决位置重建，ID 解决身份识别，它们不是同一种承诺。

## 修改操作决定借用能活多久

本章把指针、引用、迭代器和视图临时访问别处数据的行为统称为“借用”。这是解释接口的用语，不表示 C++20 会像借用检查器那样自动验证它。

先问修改是否重新分配。如果重新分配，旧元素的指针、引用和迭代器都失效。没有重新分配也不能立即放行：中间插入会影响插入点及其后的位置；尾部追加虽然保留已有元素的借用，旧的 `end()` 仍然失效。删除还要按删除位置判断。[S1] 这比背一句“扩容才失效”更可靠。

**先认识尾后位置。** `begin()` 表示序列起点，`end()` 表示最后一个元素之后的位置；`end()` 不指向一个可解引用的元素。遍历通过“当前位置是否已经到达尾后位置”判断何时停止。范围 `for` 会在循环开始时取得结束位置，不是在每轮都重新查询它。

**一个容易误判的例子。** 你先 `reserve(100)`，再遍历容器，同时在尾部追加。即使你确信本轮不会超过容量，范围 `for` 也不是天然安全：循环会使用进入循环时保存的结束位置，而追加使旧的结束迭代器失效。不要以“元素地址没动”替代完整的迭代器推理。

如果任务确实是“仅处理最初的 N 个元素，并追加结果”，可以在开始时保存原始 `size()`，按下标遍历这 N 项，每次修改后重新取得需要的位置，并检查自定义元素操作的其他影响。下面只把原始整数各复制一份到末尾；局部的 `value` 自己持有整数值，不借用容器里的元素。

```cpp
// C++20 教学片段，放在函数体内；未编译、未执行。
// 所在源文件需包含 <vector> 和 <cstddef>。
std::vector<int> v{10, 20, 30};
const auto original_size = v.size();
for (std::size_t i = 0; i < original_size; ++i) {
    const int value = v[i]; // 先取得一份值
    v.push_back(value);    // 可能重新分配，但本轮不再用旧位置
}
```

这里不保存迭代器，也不会把新追加的元素纳入本轮处理；下一轮由当前容器重新解释下标。假如改成移动前面元素的操作，或者保存的是引用，就必须重新推理。另一种更清晰的办法是读一个容器，写另一个容器，然后显式合并。方案选择取决于空间预算，但两者都必须先说明本轮处理范围。

`reserve` 的价值在于把已知的规模信息交给容器。它不是借用有效性的保证：超过容量、删除元素、销毁容器、对元素自身做其他失效操作，仍可能结束借用。`shrink_to_fit` 也只是请求减少多余容量，不能假定调用后一定等于 `size()`。[S1]

## C13.04 span 让接口更清楚 但不替你持有数据

`std::span` 是 C++20 的连续序列视图。它表达“从这里开始，有这些元素”，底层存储属于其他对象。[S1][S4] 这能让函数同时接受不同的连续存储来源，却没有把数据所有权转交给函数。

最稳妥的第一种设计，是先构造一批数据，再同步消费这批数据：

```cpp
// C++20 教学示例；未编译、未执行。
#include <iostream>
#include <span>
#include <vector>

void show(std::span<const int> batch) {
    for (int value : batch) std::cout << value << '\n';
} // 不保存 batch，不启动稍后使用它的任务

int main() {
    std::vector<int> samples;
    samples.reserve(3);
    samples.push_back(10);
    samples.push_back(20);
    samples.push_back(30);
    show(std::span<const int>{samples});
} // show 已返回，samples 才销毁
```

这里的关键不在于 `reserve(3)`。即使删掉这行，只要先完成追加、再创建视图，并且在 `show` 使用期间不修改或销毁所有者，借用关系仍然成立。预留容量是可单独评估的性能选择，消费时序才是这个接口的正确性条件。

把 `batch` 复制到异步任务里，并没有复制那些整数。视图对象还活着，背后的元素却可能已经销毁或换了地址。`span<const int>` 中的 `const` 只约束通过这个视图修改元素，不能阻止拥有 `samples` 的代码修改容器，也不能提供线程同步。若另一线程读写这些数据，还要满足 C16/C17 的同步要求。

![生产阶段拥有并修改 vector；冻结阶段结束结构修改；消费阶段借用 span；消费结束后才能复用或释放底层数据。跨阶段继续持有的异步消费者必须另有所有权与同步设计。](assets/C13-batch-phases.svg)

图 C13-B 用阶段边界让借用更容易证明。“冻结”是本例的接口约定，不是 `vector` 的内建锁。若消费者异步完成，释放边界必须跟着真实完成事件移动。

如果界面确实要稍后显示，常见选择有三种。数据小、复制便宜时，给界面一份需要的快照；一整批数据会独立流转时，把拥有数据的批次交给接收方；多个消费者确实需要同一份不可变批次时，再设计共享所有权和明确同步。不要仅为回避一次复制就让所有模块保存裸地址。反过来，也不必把每个整数都装进共享指针，额外的管理成本和复杂性要有收益支撑。

## C13.03 容器内部哪些是保证 哪些是模型

可以用“取得新存储、在新存储形成所需元素、完成后放弃旧存储”理解重新分配。这个模型解释了为什么旧地址不能继续使用，也暴露出失败问题：新元素形成到一半时发生异常，旧序列还能不能恢复？实际实现可能有专门优化，元素构造顺序也受操作和别名情况影响；不要把图中步骤当作实现源码。

对于一般 `T`，不能把迁移简单写成 `memcpy`。对象可能持有资源，可能禁止复制，也可能需要执行移动构造。标准库必须满足适用类型和操作的语义要求；“连续存储”没有取消对象语义。C++ Core Guidelines 的容器建议和字节复制警示可作为工程阅读补充，但它们不是 ISO 规范。[S5]

**进阶小桥：移动为什么影响异常保证。** 复制通常保留源对象不变；移动可能把资源从源对象转走。设想已经移动了前几条记录，下一条的移动构造却抛出异常。如果恢复本身还可能抛出，就不能轻易承诺“整批像没发生过一样”。WG21 早期论文 N2855 用这个问题说明移动与异常安全的冲突；它是设计背景，不是今天的最终接口规范。[S6]

对本章最相关的“尾部插入单个元素”，C++20 条款把无效果保证与类型条件联系起来：满足复制插入要求，或移动构造不抛出时，异常不改变容器；对不可复制插入的类型，如果它的移动构造抛出，条款允许效果未指定。[S1] 这里的“复制插入”是带分配器的库要求，不要仅凭看到一个拷贝构造函数就下结论。

因此，分析某个自定义记录类型之前，要先看资源成员如何复制或移动，再看异常能从哪里出现。`noexcept` 是语义承诺，不是提速开关；只有确实不会让异常逃出时才该使用。关于“不抛出函数中异常逃出”的后果，参见 C14 和标准的异常规范条款。当前样章没有编写自定义分配器，也没有声称测得复制或移动次数。

同样要拒绝“vector 永远按 2 倍扩容”“vector 对象永远正好三个指针”这样的结论。某个库版本的代码或调试器布局可以帮助研究该实现，却不能替其他标准库、调试模式、分配器和应用二进制接口（ABI）作保证。本章图只表达元素区、容量与借用关系。

## 从摊还复杂度走到延迟预算

尾部追加的摊还常数复杂度，描述一串操作的总成本如何分摊，并不承诺每一次追加耗时接近。[S1] 日志程序的界面卡顿关注的是某一批何时完成，单次慢操作就可能决定体验。

可以自己推导一个简化模型：假设容量每次翻倍，并且迁移一个元素计一个单位成本。增长到 N 个元素前，扩容搬移的规模像 1、2、4、8……累加，总数仍与 N 同阶。这解释了增长策略为何能摊平成本。它既不是某家标准库的实测增长序列，也忽略了元素自身构造、分配器、页面和线程调度的代价。

如果每次追加之前都请求 `reserve(size() + 1)`，你可能破坏原本的增长余量。在按请求量供给容量的实现模型下，每次都迁移，成本会像 1+2+…+(N−1)，进入平方级。正确的教训是利用可信的批量规模，而不是给每个 `push_back` 都加一个“优化”调用。

连续访问通常值得优先评估，因为它给数据布局和遍历提供了简单的起点；这也是 C++ Core Guidelines 建议默认考虑 vector 的背景之一。[S5] 但本章不宣称它比链表快某个倍数。元素是否很大、是否间接指向别处、访问是否随机、需要多少中间插入，都会改变成本。

**一个尚未执行的测量计划。** 对同一份解码输入比较“自然增长”和“已知记录数时一次 reserve”。先检查得到的记录内容完全一致，再计记录数、实际容量变化、批次耗时和峰值内存；若关注逐条追加中的少量特别慢的操作，也就是延迟的长尾，还要单独设计低开销采样，不能只看批次平均数。至少记录编译器、标准库版本、优化选项、CPU、操作系统、输入分布和重复次数。释放旧块、页面首次触碰和测试计时本身的开销都可能影响结果。冷热条件分别报告，避免把第二次恰好缓存命中算成方案优势。

如果使用 C13 的仪表化记录类型统计复制/移动次数，应把它与生产类型分开：添加日志和计数器会改变对象成本、优化空间，甚至异常属性。测量回答的是特定环境里的问题，复杂度回答的是增长趋势，二者不能互相冒名。

## 回到设备日志查看器作工程选择

假设接收模块按批解析、界面需要稍后读取。本章首先推荐把批次所有权和消费完成时间说清，再尝试预留容量。若界面只需要标题和时间戳，复制这两个字段可能比共享整批数据更容易维护。例如标题接口可设计为 `void enqueue_title(std::string title)`，并约定实现把字符串值移动或复制到界面队列自己的存储中，保持到显示完成；仅仅按值接收后又保存参数地址，仍然是错误实现。若需要完整记录，传递拥有数据的批次，并在显示期内保持它稳定，能减少跨模块的隐含借用。

只有确有“元素位置必须长期稳定”的需求时，才进一步比较间接存储、句柄表或其他容器。比如 `vector<unique_ptr<Record>>` 能把容器元素的迁移与被指向记录的地址分开，但它引入间接访问与通常的单独分配；删除相应记录仍会使借用失效。换容器并没有取消生命周期问题。

对内存紧张的设备或有明确实时上界的循环，还要问批次上限是多少、是否允许运行期分配、超限时怎样处理。提前 `reserve` 只能安排这一个容器的容量，不能证明整条调用链没有分配，更不能单独证明最坏执行时间。本例是一般应用程序教学，不是硬实时安全论证。

## 五个故障信号及其排查方向

1. **数据量大才乱码。** 查长期保存的指针、引用、迭代器和视图，回溯它们与每次容器修改的先后关系。相关性只是线索，先找到具体失效边界。
2. **reserve 后越界写仍不报错。** 检查下标是否小于 `size()`，不要拿 `capacity()` 作为访问上限。工具没有报告不等于满足前置条件。
3. **不用扩容也遍历异常。** 查插入点、删除点和被保存的结束迭代器；范围循环也需要完整分析。
4. **用了 span 仍有悬空。** 追踪底层所有者和异步任务实际结束时间，别只看视图变量的作用域。
5. **平均值更好但偶尔卡顿更重。** 把重新分配、页触碰、解码和界面调度分开记录；平均吞吐不回答尾延迟预算。

AddressSanitizer 可帮助发现被执行路径上的越界和释放后使用，调试迭代器模式可补充部分容器误用诊断。[S7][S8] 两者都不能替代规范推理和覆盖分析。尤其不能承诺一个工具能发现全部“容量内但 size 外”的访问或全部失效迭代器。GCC 的调试模式还可能改变容器大小和行为，应按官方要求处理调试与非调试构建的边界；不要直接把它的耗时当作发布版本结果。[S8]

## 六层面试追问链

下面不是六个孤立定义，而是同一故障逐步增加约束。它适用于国内 C++ 校招、转岗或经验岗的练习设计，不声称某企业必考，也没有用招聘样本推算出现频率。

**第一层 描述现象。** `size` 与 `capacity` 差在哪里？回答应落到“哪些元素可以访问”，而不只说一个是大小一个是容量。追问：空容器 `reserve(100)` 后能写第 0 项吗？参考回答：不能，先创建元素。

**第二层 推导机制。** 为什么值没删掉，地址却失效？参考回答：元素序列仍存在，但成功重新分配结束了旧地址对应的访问资格，需从当前容器重新取得位置。追问：怎样构造不依赖增长倍数的例子？参考回答：记录容量，在上限允许时请求更大的容量，并讨论成功与异常两条路径。

**第三层 找出反例。** 容量足够就能边范围遍历边追加吗？参考回答：不能凭这一点保证；还存在结束迭代器失效。追问：只处理原始元素怎样表达？参考回答：固定原始数量、按需求重新取得位置，或分离读写容器，并说明修改对身份的影响。

**第四层 分析失败。** 迁移时元素移动构造可能抛出，会怎样？参考回答：先明确是哪种操作，再看复制插入和不抛出移动等条件。不能把所有 vector 修改都说成强保证（失败后无可观察变化），也不能认为加 `noexcept` 就修好了资源设计。

**第五层 设计实验。** 一次预留为什么可能有帮助，怎样证明？参考回答：提出减少重新分配的假设，固定负载和环境，校验内容，报告延迟分布与内存；拒绝把推导的倍率写成测得的加速比。

**第六层 交付设计。** 界面需要异步展示日志，内存又有限，选什么？参考回答：先问需要哪些字段、保存多久、谁释放、谁能修改；小快照、独占批次或不可变共享批次各有适用条件。优秀回答给出可验证的结束边界和超限策略，而不是只报容器名称。

## 练习与自检

先遮住答案，写出你的推理依据。正确结论至少应带一个前提。

**E1 数量和访问。** `vector<int> v; v.reserve(8); v.resize(3);` 成功后，`size()` 是多少？`capacity()` 一定等于 8 吗？哪些下标可用？

**E2 不扩容的追加。** 已知 `v` 有三个元素，容量至少为 10。保存 `p=&v[0]` 和 `e=v.end()`，再追加一个元素并成功返回。`p` 与 `e` 各能否继续按原来用途使用？

**E3 视图是否拥有。** 函数创建局部 vector，返回指向其中元素的 span。调用者马上遍历。为什么“马上”不是有效修复？写出两种不同所有权的接口方案。

**E4 删除后的身份。** 容器记录按时间排序，你保存下标 5 作为某条记录的身份。之后在前面删除一条。即使所有访问都在边界内，还可能错在哪里？

**E5 设计测量。** 同事只展示两次执行的总耗时，宣布 reserve 使系统快一倍。列出四项最先要补的证据，并说清哪项能验证正确性。

### 参考答案

**E1。** `size()` 为 3；容量至少为 8，不保证刚好 8；只有下标 0、1、2 对应元素。答案必须区分成功返回与分配失败。这里的 `int` 元素值可按相应初始化规则进一步分析，但不是本题判断可访问范围的前提。

**E2。** 在本题已知不重新分配的尾部追加条件下，`p` 仍能访问原先的第一个元素；旧的 `e` 失效，应重新调用 `end()`。如果改成在开头插入，不能沿用这个结论。

**E3。** 函数返回后局部容器已销毁，“马上”也晚于这个生命周期结束点。接口可以是 `std::vector<int> make_samples()`，返回值由调用者持有；也可以是 `void fill_samples(std::vector<int>& out)`，由调用者提供并持有容器，函数同步填充且不保留借用。它们是未执行的接口示意，第二种还需明确覆盖还是追加、错误处理及异步使用限制。

**E4。** 下标表示位置，前面删除后位置会变化。程序可能合法读取另一条记录，因此内存诊断工具未必有理由报错。稳定 ID 与查找或受约束的句柄策略才是在解决身份问题。

**E5。** 先补输出等价性、输入分布与规模、工具链和硬件配置、重复测量及离散程度；再看容量变化与内存开销以验证机制。输出等价性验证没有为了速度改变任务。两次时间没有提供可靠的波动范围，不能外推系统整体表现。

**自检出口。** 如果你能在一张纸上标出“谁拥有数据、何时修改、谁借用、何时结束”，再给性能主张设计一次可证伪的实验，就可以继续 C14 的失败保证或 C20 的测量方法。若仍把“没崩溃”当作“有效”，先重做 E1—E3。
